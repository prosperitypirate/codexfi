# DevMemBench

DevMemBench is a benchmark developed by [ProsperityPirate](https://github.com/prosperitypirate) specifically for codexfi — available in the [`benchmark/` directory](https://github.com/prosperitypirate/codexfi/tree/main/benchmark) of the repository. It measures how reliably codexfi recalls facts across coding sessions: 200 questions across 8 categories that map directly to how you use memory day-to-day.

> **Results.** The full methodology, every run, and the latest scores live in the [benchmark README on GitHub](https://github.com/prosperitypirate/codexfi/tree/main/benchmark). Results for the 1.0 (Claude Code) architecture — on-device embeddings and extraction through Claude Code — are being finalised and will be published there. Historical runs from 0.7.x (OpenCode, Voyage embeddings, API-key extraction) are kept for reference and are not directly comparable.

## What each category measures

Each category corresponds to something the memory system does during a real session:

| Category | What it means in practice |
|---|---|
| `tech-stack` | Remembers your framework, language, and tooling choices |
| `architecture` | Recalls system design decisions and component relationships |
| `preference` | Keeps track of your personal coding and workflow preferences |
| `abstention` | Doesn't hallucinate answers when something isn't in memory |
| `session-continuity` | Carries facts from one session into the next |
| `knowledge-update` | Replaces stale facts when you switch tools or change approaches |
| `error-solution` | Retains bug fixes, gotchas, and debugging approaches |
| `cross-session-synthesis` | Combines facts that were spread across multiple sessions |

## Known limitation: cross-session synthesis

`cross-session-synthesis` has historically been the hardest category. It tests questions like "list every preference you've seen me mention across all our sessions" — queries that require enumerating facts scattered across many separate sessions with different phrasing.

A single semantic search surfaces the most relevant memories but may miss facts phrased differently from the query. codexfi detects list-style prompts and additionally pulls memories by type, which helps — but for an exhaustive list of one kind of memory, ask Claude to use `memory_list` (for example, all `preference` memories) rather than relying on semantic retrieval alone.

## Benchmark dataset

<DocsBenchmarkDataset />

The benchmark uses a synthetic codebase history spanning two realistic projects:

- **`ecommerce-api`** — FastAPI + PostgreSQL + Redis + Stripe. Sessions covering authentication, product catalog, shopping cart, and checkout flow (Jan–Feb 2025).
- **`dashboard-app`** — Next.js 15 + Recharts + SWR. Sessions covering analytics dashboard, chart components, and data fetching (Jan–Feb 2025).

Sessions were written to reflect realistic developer conversations — including preference statements, architectural decisions, error debugging, and knowledge updates (for example, migrating from one ORM to another mid-project). The 200 questions are designed to stress memory across session boundaries, not just within a single conversation.

## Methodology

<DocsBenchmarkPipeline />

The benchmark runs a five-phase LLM-as-judge pipeline:

1. **Ingest** — the synthetic sessions are ingested into a fresh, isolated codexfi memory store using codexfi's own extraction and embedding pipeline
2. **Search** — for each of the 200 questions, codexfi's retrieval pipeline is called with the question as the query
3. **Answer** — an LLM answers using only the retrieved memory context (no access to the original session transcripts)
4. **Evaluate** — a judge LLM compares the answer against ground truth and scores it `correct` or `incorrect` with an explanation
5. **Report** — scores are aggregated by category and written to `report.json`

The answering step is intentionally constrained — if codexfi's retrieval doesn't surface the right memory, the answer will be wrong. This makes the benchmark a direct measure of retrieval quality, not LLM reasoning ability.

### Modes

- **Retrieval** (default) — answers from semantic search over the store.
- **Block quality** (`--mode block-quality`) — answers from the assembled structural `[MEMORY]` block only, isolating what session-start injection provides.
- **Memory Bank** (`--mode memory-bank`) — does codexfi add value on top of a Memory Bank? Compares no memory, a simulated Memory Bank alone, codexfi alone, Memory Bank + codexfi, and the full transcript as an upper bound.

Retrieval and block-quality scores are not comparable with each other; see the benchmark README for details.

## Running the benchmark yourself

**Prerequisites**

- [Bun](https://bun.sh) ≥ 1.2
- [Claude Code](https://code.claude.com), logged in — with `BENCH_LLM_BACKEND=claude-cli`, the answer and judge calls run through your Claude Code login (or use `ANTHROPIC_API_KEY` with the default `api` backend)

**Run**

```bash
cd benchmark
bun install                                   # first time only

# keep the run's store away from ~/.codexfi
export CODEXFI_DATA_DIR=/tmp/bench-store BENCH_LLM_BACKEND=claude-cli

bun run bench run --limit 10 -r smoke         # quick smoke test
bun run bench run -r my-run                   # full 200 questions
bun run bench run -r mb-v1 --mode memory-bank # Memory Bank vs codexfi
```

Results are written to `benchmark/data/runs/<run-id>/report.json`. Named runs are checkpointed after each phase, so an interrupted run resumes with the same `-r <id>`. See the [benchmark README](https://github.com/prosperitypirate/codexfi/tree/main/benchmark) for every flag and environment variable.
