# Architecture Overview

codexfi is a [Claude Code](https://code.claude.com) plugin made of three plain pieces: **hooks** that inject memory and queue work, a **short-lived background worker** that does the slow part, and an **MCP server** that gives Claude explicit memory tools. There are no servers to run, no ports, no Docker, and no API keys — extraction runs through your own Claude Code login and embeddings run on your machine.

## Claude Code hooks

| Claude Code event | What codexfi does | Typical time |
|-------------------|-------------------|--------------|
| `SessionStart` (startup / clear / compact) | Injects the structured `[MEMORY]` project picture; queues auto-init for a brand-new project | ~110 ms |
| `SessionStart` (resume) | Nothing — earlier context is replayed from the transcript | — |
| `UserPromptSubmit` | Embeds the prompt locally, searches project + user scope, injects memories not yet shown this session | ~250 ms |
| `Stop` | Queues a turn job and starts the worker if none is running | ~90 ms |
| `PreCompact`, `SessionEnd` | Queues a session-summary job | ~90 ms |

Every hook fails silently — a codexfi problem never blocks your session. Hook traffic from subagents is ignored, so exploration noise never becomes memory.

## Data flow: retrieval

### Session start

On `startup`, `clear`, and after `compact`, codexfi lists the project's structured memories and your user preferences and injects them as the `[MEMORY]` block (Project Brief, Architecture, Tech Context, Product Context, Progress & Status, Active Context, Recent Sessions, User Preferences). The block is kept under Claude Code's 10,000-character limit for injected context by dropping whole trailing items — never cutting a fact in half.

If the project has a `memory-bank/`, the structured sections are skipped (the bank already carries them) and only session summaries newer than your last bank save are added. See [Memory Bank](/docs/guides/claude-code-setup#memory-bank).

If the project has no memories yet, an **auto-init** job is queued: the worker reads 28 common project files (README, package.json, Dockerfile, tsconfig, monorepo configs, agent instructions such as `CLAUDE.md`, and more) plus the last 20 git commits, and seeds the first memories.

### Every prompt

Each prompt is embedded on-device and searched against both the project and user scopes in parallel. Matches go into a **Relevant to Current Task** block — minus anything already injected in this session, since it is still in Claude's context. List-style prompts ("list all my preferences") additionally pull memories by type, so enumeration questions aren't limited to the top semantic hits.

When you ask Claude to remember something, codexfi adds a short note pointing it at the `memory_add` tool.

## Data flow: storage

### After every turn

1. The `Stop` hook queues a job and returns immediately.
2. A single background worker (one per machine, guarded by a lock file) reads the transcript **from where it last stopped** — a byte cursor, so each turn is extracted exactly once. Long turns are split into windows on message boundaries instead of being truncated.
3. Each window goes to the LLM — `claude -p --safe-mode` with Haiku by default — which returns a JSON array of typed facts.
4. Each fact is embedded locally.
5. **Deduplication** — a fact very close to an existing memory updates it in place instead of adding a copy.
6. **Supersede** — nearby memories are checked by the LLM; stale ones are marked `superseded_by` the new fact.
7. **Aging** — `progress` and `active-context` keep only the latest; `session-summary` keeps the newest 3 and condenses older ones into `learned-pattern`.

The worker exits when the queue is empty. codexfi's own `claude -p` calls run with `--safe-mode` (no plugins or hooks) and `CODEXFI_DISABLE=1`, so they can never trigger codexfi recursively.

### Session summaries

`PreCompact` and `SessionEnd` queue a summary job: the worker first extracts any turns not yet processed, then writes a `session-summary` describing the arc of the session.

## Compaction survival

<DocsCompactionSurvival />

When Claude Code compacts a conversation:

1. `PreCompact` queues a session summary, so nothing from the compacted turns is lost.
2. `SessionStart` fires again with source `compact`, and codexfi re-injects the full `[MEMORY]` project picture into the fresh context window.
3. The per-session "already shown" list is reset, so relevant memories can surface again on the next prompt.

## Explicit tools (MCP)

The plugin ships a stdio MCP server with four tools — `memory_search`, `memory_add`, `memory_list`, and `memory_forget`. Claude uses them when it needs history that isn't already in context or when you ask it to remember something. See the [Memory Tools reference](/docs/api-reference/memory-tool-api).

## Technology stack

| Component | Technology |
|-----------|-----------|
| Host integration | Claude Code plugin — hooks, MCP stdio server, skill |
| Extraction LLM | Your Claude Code login via `claude -p --safe-mode` (Haiku by default); Anthropic API optional |
| Embeddings | On-device ONNX via transformers.js — `jina-embeddings-v2-base-code`, 768 dimensions; local-only |
| Storage | SQLite with WAL mode — built in to the runtime (`bun:sqlite` on Bun, `node:sqlite` on Node), no native npm dependencies |
| Search | Exact nearest-neighbor cosine similarity over Float32Array BLOBs, blended with recency |
| Runtime | Bun, or Node ≥ 22.5 — picked automatically by the launcher |
| Validation | [Zod](https://zod.dev/) schemas for memory records |

### Why SQLite?

SQLite ships **built in** to both Bun and Node — no native binaries to rebuild per platform, nothing to break on upgrades. The store loads `bun:sqlite` under Bun and `node:sqlite` under Node; both drivers share the same on-disk format, so the same `~/.codexfi` database works under either runtime.

WAL (Write-Ahead Logging) mode handles concurrency: several Claude Code sessions can read the store at once while the single background worker writes, with writers safely queued via `busy_timeout`. This is validated by stress tests that spawn 20 real OS processes against the same database file.

## File structure

```
plugin/
├── .claude-plugin/plugin.json   manifest (+ MCP server declaration)
├── hooks/hooks.json             SessionStart · UserPromptSubmit · Stop · PreCompact · SessionEnd
├── scripts/run.sh               runtime launcher (bun → node ≥ 22.5 → silent no-op)
├── skills/memory-bank-sync/     "save bank" helper skill
├── dist/codexfi.js              single-file bundle (CLI + hooks + worker + MCP)
└── src/
    ├── claude/       Claude Code integration
    │   ├── hooks.ts        hook handlers (read hooks inject, write hooks enqueue)
    │   ├── context.ts      SessionStart block + per-prompt block (Memory-Bank aware, per-session dedup)
    │   ├── transcript.ts   incremental transcript reader (exactly-once byte cursor)
    │   ├── worker.ts       detached single-instance job worker (extraction, summaries, auto-init)
    │   ├── state.ts        sessions/, queue/, worker.lock, logs/ under ~/.codexfi
    │   ├── mcp.ts          stdio MCP server: memory_search / memory_add / memory_list / memory_forget
    │   └── runtime.ts      init, tags, disable switches, 10k-cap fitting
    ├── llm.ts        Claude via `claude -p --safe-mode` (default) or Anthropic API
    ├── embedder.ts   local, on-device ONNX embeddings only; model-specific thresholds
    ├── extractor.ts  extraction / summary / contradiction / condensation prompts → JSON
    ├── store.ts      ingest, addMemory, dedup, supersede, aging, search, re-embed migration
    ├── store/        SQLite (bun:sqlite | node:sqlite) vector store, WAL, migrations
    ├── services/     memory-bank detection, query intent, [MEMORY] formatter, privacy, tags
    ├── cli/          `codexfi status | list | search | stats | export | forget | dashboard | install`
    └── dashboard/    local web dashboard
```
